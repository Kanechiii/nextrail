# Shared authentication request protection

This is an **opt-in, backend-only** Phase 26 security improvement. The existing
single-instance in-memory limiter is the default, so guest discovery, saved
learning, session contracts, and previously accepted local development behavior
remain unchanged. A configured SQLite file-backed limiter shares fixed-window
request budgets across API workers/connections using atomic SQLite transactions.

## Scope and activation

- Requires a real, durable `NEXTRAIL_DB_PATH` (not `:memory:`).
- Requires `NEXTRAIL_RATE_LIMIT_HMAC_KEY`: exactly 64 **lowercase hexadecimal**
  characters representing a 32-byte key generated by a secure random source.
- Keep the same key for all workers sharing the database; changing the key
  fails startup rather than silently allowing a fresh request budget.
- Keyed HMAC-SHA256 digests of the direct peer address are stored; no raw client
  IP, bearer token, email, or forwarded IP header is written to the limiter.
- Atomic writes enforce the existing route-specific limits across workers.
  Capacity exhaustion, unavailable SQLite storage, and clock rollback fail
  closed with HTTP 429/503 instead of bypassing the limiter.
- The limiter stores at most 4096 active route/client/window entries; expired
  entries are pruned when capacity is reached. It does not introduce new
  tables in the learning or authentication schema version contracts.

Generate a key in **your own PowerShell shell**, without printing or committing
the value to GitHub:

```powershell
$env:NEXTRAIL_RATE_LIMIT_HMAC_KEY = [Convert]::ToHexString([Security.Cryptography.RandomNumberGenerator]::GetBytes(32)).ToLowerInvariant()
```

Use an existing parent directory for the database and opt into durable storage:

```powershell
$env:NEXTRAIL_REQUIRE_DURABLE_STORAGE = "true"
$env:NEXTRAIL_DB_PATH = "data/nextrail-local.sqlite"
```

Never check the key or a real account database into source control.
On restart, the same key must be available; replacing it requires a separate
approved key-rotation/migration procedure. Do not use the shared production
database for disposable acceptance tests.

## Boundaries

This does not make authentication production-ready by itself. The limiter is
intended for a single host/shared SQLite deployment. A multi-host production
deployment needs independently approved distributed rate limiting and
connection architecture. Proxy and TLS termination, trusted origins, account
email verification, recovery delivery, security monitoring, data retention
and abuse controls remain release blockers.

Clients behind one NAT may share an address budget. Forwarded IP headers are
**intentionally not trusted**; configure a vetted trusted-proxy deployment
boundary in a separate reviewed change before deploying behind a reverse
proxy. SQLite write contention produces a denial rather than bypass.

## Verification

From the existing Nextrail root on a clean checked-out revision:

```powershell
python -m unittest discover -s scripts -p "test_*.py" -v
python scripts/validate_repository.py
python scripts/validate_catalog.py
python scripts/validate_discovery.py
python scripts/evaluate_pathways.py
python scripts/verify_source_authorizations.py --sources data/sources.sample.json --authorizations data/provider-authorizations.sample.json
Set-Location apps/web
npm test
npm run build
Set-Location ../..
```

After **manual squash merge** and a passing main CI run, sync your existing
local checkout without using extra worktrees:

```powershell
git status --short
git fetch origin
git switch main
git pull --ff-only origin main
```

If Git reports uncommitted changes or diverged history, stop rather than
resetting, cleaning, force-pulling, or popping any preserved stash.
